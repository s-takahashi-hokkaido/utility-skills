# Clean Architecture

## 解決したい問題

ドメインロジックがDBやControllerに依存しているために、DBやControllerのコードを変更するとドメインロジックが正しく動作しなくなる。

## 効果

- 他のモジュールに依存しているほど依存モジュールの変更時に壊れやすくなり、依存が少ないほど壊れにくくなる（安定依存原則）。
- 他の技術層がドメイン層（Entity）に依存する構造にすることで、ドメイン層が相対的に最も変更に対して安定する。

## 相応しくない状況

ドメインロジックがDBやControllerにあまり依存していない、または仕様的にほぼ安定しており将来変更する機会があまりないコードに対しては旨味がない。

## 判断の手がかり（補足）

問題があることを示すシグナル:

- ORMのモデルやControllerの中に、業務ルールや計算ロジックが直接書かれている
- DBのスキーマ変更、フレームワークの更新、API仕様の変更で業務ロジックが壊れたことがある
- DBやWebサーバーを立ち上げないと業務ロジックをテストできない
- DBや外部サービスを差し替える予定がある、またはその可能性が高い

問題がないことを示すシグナル:

- 業務ロジックがほとんど無い（データの出し入れが中心）
- 業務ロジックがすでに純粋な関数やモジュールとして分離されている
- 使い捨てのスクリプト、PoC、短期間だけ使うツール
- 仕様が安定していて、今後の変更予定がほとんどない

## 部分適用の選択肢

- 層を全部そろえず、業務ロジックを純粋なモジュールに切り出し、DBアクセスはインターフェース越しにする（依存の向きだけを逆転させる）
- 変更頻度が高い、または壊れたときの影響が大きいモジュールにだけ適用する
